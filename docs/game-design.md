# 基本設計

このゲームの企画と、設計の判断基準をまとめたドキュメントです。
このファイルはオーナーが管理します。変更したいときは、issueで提案してください。

---

## 1. ゲームコンセプト

Coffee Inc 2 を参考にした、飲食店チェーンの経営シミュレーションゲーム。
1店舗から始めて、チェーン化、上場、ホールディングス化へと拡大していく。

**このゲームが一番力を入れるのは、ホールディングス段階のシナジーと効率化です。**
規模が大きくなったら他業種の飲食店を買収し、外食大手の手法（セントラルキッチン、原料の共通化、仕組みの横展開など）を使って利益率を上げていく。

- ゴールはない。拡大を目指し続ける。
- 倒産はありうる。
- 遊び方は、**権限移譲を進めるほど放置寄りになっていく**。
- 時間は週単位で進む。プレイヤーが「次の週へ進む」ボタンを押して進めるのが基本（全フェーズ共通）。自動で進むモードも用意する。

## 2. 根幹の設計思想

### 「リアルさだけを追及しない」

- 目的は**プレイヤーを楽しませること**。
- 現実の経営に寄せる必要はない。
- ただし**もっともらしさは必要**。
  - 「値上げすると客が減る」「好立地は家賃が高い」のような、**誰でもなんとなく知っている常識**には必ず沿わせる。
  - そこが崩れると、プレイヤーは夢から覚めてしまう。
- 迷ったら「リアルかどうか」ではなく「もっともらしく、かつ楽しいか」で判断する。

### 楽しさの2本柱

1. **数値が伸びる快感**（クッキークリッカー型）
2. **選択肢が増える快感**（アンロック型）
3. **効率化の快感**（ファクトリオ型）

新しい仕組みを提案するときは、このどれに効くのかを必ず説明すること。面白さが説明できる要素しかいれない。

効率化の快感について

このゲームの一番の売りであるホールディングス段階で、主役になる楽しさ。 他業種のブランドを買収し、シナジーを生み出すときに強く効く。

「数値が伸びる」との違い：「数値が伸びる」は規模の拡大（店が増える、売上が増える）。「効率化」は同じ規模のまま、無駄が消えて利益率が上がること。足し算ではなく掛け算の楽しさ。
組み合わせを見つける楽しさ：「この業態とこの業態は同じ食材を使うから、まとめれば安くなる」のように、プレイヤーが自分で相性の良い組み合わせを見つけたとき、一番気持ちよくなるように設計する。
一手で全体が良くなる楽しさ：1つの判断（工場を建てる、DX）が、多くの店や会社にまとめて効く。
見える化：効率化の効果は、導入の前と後で比べられる形で必ず見せる（例：利益率が何%から何%に上がったか）。効果が見えない効率化は、楽しさにならない。
判断の余地を残す：どのブランドを買えばシナジーが大きいか、という選択に正解が1つだけにならないようにする。業態の組み合わせ方で、プレイヤーごとに違う「自分の勝ちパターン」が生まれるようにする。

## 3. 設計時に意識する3つの階層

すべての設計の議論とissueで、**どの層の話かを明示すること**。

| 層 | 対象 | 意識すること |
|---|---|---|
| **A** | ゲーム全般 | トレードオフ軸、インセンティブ設計、わかりやすさ |
| **B** | シミュレーション | 楽しさを優先。リアルにしすぎない。 |
| **C** | 経営ゲーム | チュートリアル |

1つのissueが複数の層にまたがる場合は、主な層を1つ選び、関係する層も書く。

## 4. フェーズと権限移譲

フェーズが進むほど、プレイヤーの操作は「細かい個別操作」から「大きな方針・戦略」に移っていく。
**権限移譲そのものを、成長の実感として設計すること。**

| フェーズ | 規模 | プレイヤーが主に決めること | 任せられるもの（例） |
|---|---|---|---|
| 1. 1店舗 | 自分の店 | 出店場所、設備と内装、価格、店員の人数と時給、店長の選任と解雇など個別の操作 | なし（自分でやる） |
| 2. チェーン | 複数店舗・1業態 | 出店場所、店舗の方針 | 店長に日々の運営を任せる |
| 3. 上場 | 大規模チェーン | 資金の使い道、本部の仕組み | 本部・役員に方針の実行を任せる |
| 4. ホールディングス | 複数業態・複数会社 | 買収、業態の組み合わせ、シナジー戦略 | 事業会社の社長に会社ごと任せる |

- 1.の段階から店長に運営を任せられるようにする。
- 店員は**人数と時給だけ**で表す。名前と能力値を持つのは**店長**。
- 店員の人数と時給は、フェーズ1からプレイヤーが調整できる。士気は店ごとの値として持つ。
- 店長は、プレイヤーが選任しない限りいない（プレイヤーが直接運営する）。店長は、その店が開店した週から雇える。
- 4フェーズすべてを、最初から**概要レベル**で設計する。
- 詳細設計と実装は、**フェーズ1から順に**進める。
- データ構造は最初から、フェーズ4（複数業態・複数会社・共通の仕入れ）に対応できる形にする。詳しくは `docs/architecture.md` を参照。
- 権限移譲にはトレードオフを持たせる（例：手間が減る代わりに、自分でやるより少し効率が落ちる）。

### フェーズの扱い

- 「フェーズ」は、設計の段階でユーザ体験などを考えるために、便宜的に使っている言葉。**ゲームの中には持たない。**
- フェーズに関するデータ構造は持たない。ゲーム側が現在のフェーズを示すこともしない。
- フェーズの移り変わりは**シームレス**にする。区切りや関門を置かない。
- 設計のレベルでは「いまどのフェーズの話か」を考える。ゲームに落とし込む段階で、シームレスになるように変える。
- 各フェーズでのプレイヤーの行動の誘導は、資金面などの制約という形で、自然に行う。

## 5. 設計ルール

### 5.1 用語（C層）

現実の経営手法を取り入れるときは、必ず次の3点セットに翻訳する。

1. **現実の手法**（設計資料の中だけで使う）
2. **効果の一行説明**（何がどう良くなるか）

例：

| 現実の手法 | 効果 |
|---|---|
| DXの横展開 | 1つの店・会社で導入した改善が、他の業態にも効く |
| 原料の共通化 | 同じ食材を使う店が多いほど、仕入れ値が下がる |
| セントラルキッチン | 店での調理の手間が減り、味がそろう |

### 5.2 再現しないもの（B層）
現在検討中

以下は、現実にはあっても**ゲームでは再現しない、または最小限にする**。

- リストラ、人員整理（店長の解雇は操作として入れる。下の「再現するもの」を参照）
- 食中毒や不祥事などの事件・炎上
- 複雑な会計・税務・法律の手続き
- 上場の面倒な手続き

これ以外にも「現実では辛いが、ゲームにしても楽しくない」要素を見つけたら、入れずに提案として挙げること。
逆に楽しいものや、プレイヤースキルを要求する要素は積極的に入れていきたい。

再現するもの（例）
- M&Aの手続きや統合の混乱
  - 反対、のれん代のコンセンサスなど
- 株主からの強い圧力（経営の効率化のインセンティブを与える）
- 店長の解雇、店員の人数を減らすこと（解雇）、時給の変更
  - 店の士気に影響する

これらの非構造的な部分は設計を重点的に行う。

### 5.3 倒産と放置の両立

- 倒産はありうる。
- 危険が近づいたら早めに分かる、任せた相手が守りに入る、などの仕組みを用意する。具体案は設計issueで提案すること。
- 倒産は理不尽ではなく、「自分の判断の結果」と納得できるものにする。

### 5.4 数値の伸び方

- 数値は大きく伸びてよい（夢を見せる）。ただし、伸び方にはフェーズごとの**天井**を持たせる。
- 天井をこじ開けるのは、次のフェーズや新しいアンロック（新業態、買収、シナジーなど）にする。
- 天井と伸び方の考え方は、早い段階で設計issueとしてまとめる。

### 5.5 名前と権利

- 実在の企業名、ブランド名、Coffee Inc 2 の固有の名前や素材は、ゲーム内に使わない。
- 参考にするのは**仕組みや考え方だけ**。ゲーム内の会社とブランドはすべて架空にする。

## 6. 迷ったときの優先順位

1. プレイヤーが楽しいか、夢を見られるか
2. 誰でも知っている常識に反していないか（もっともらしさ）
3. わかりやすいか（難しい用語を出していないか）
4. 実装がシンプルか

判断できないときは、勝手に決めずに、issueの「未決事項」に書いてオーナーに聞くこと。
