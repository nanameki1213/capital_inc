# 「フェーズ」は設計上の言葉で、ゲームの中には持たない

- 日付：2026-11-17
- 判断した人：オーナー
- 関係する issue：すべて（特に #2、#5、#11、#12、#21、#22）

## 判断内容

1. **フェーズに関するデータ構造は持たない。** 「いまどのフェーズか」を表す値を、ゲームの状態に入れない。
2. **ゲーム側が、現在のフェーズを示すことはしない。** 画面にも出さない。
3. **フェーズの移り変わりはシームレスにする。** 区切りや関門を置かない。
4. 「フェーズ」は、設計の段階で、ユーザ体験などを考えるために便宜的に使っている言葉。設計のレベルでは「いまどのフェーズの話か」を考えるが、ゲームに落とし込む段階でシームレスになるように変える。
5. **各フェーズでのプレイヤーの行動の誘導は、自然に行う。** 資金面などの制約という形にする（例：お金が足りないうちは2店舗目を出せない）。
6. フェーズ1は、60週までは引っぱらない（#12）。

## 理由

オーナーからの指示。認識を合わせるための重要な事項として示された。

## 設計での守り方

- 「フェーズNへ進む条件」という書き方をしない。「その行動（2店舗目の出店、上場、買収）が、どんな制約のもとでできるようになるか」として書く。
- 「フェーズNでアンロック」は、ゲームの中の理由（お金、店舗数、評判、利益の安定など）による解放として書く。
- チュートリアルは「フェーズの入口」ではなく、「その仕組みに初めて触れたとき」に出す。
- issue のラベル `phase:*` と、文書の章立ての「フェーズ」は、設計上の整理としてそのまま使う。

## 影響

- `docs/design/overview.md` の 2章（特に 2.6）と 8章を直した。
- #21 を「2店舗目への自然な移り方」として書き直した。
- `docs/game-design.md` 4章に「フェーズの扱い」を追記した（オーナーの指示による）。
