# コーディングルール

コードを書くときに守るルールです。
このファイルはオーナーが管理します。変更したいときは、issueで提案してください。
構成やモジュール間のルールは `docs/architecture.md` を参照してください。

---

## 1. 型

- `tsconfig.json` は `strict: true`。加えて `noUncheckedIndexedAccess: true` を有効にする。
- `any` は使用禁止。外部から来るデータは `unknown` で受けて、Zodで検証する。
- 型アサーション（`as`）は、理由をコメントに書ける場合だけ使う。
- 状態の種類はユニオン型で表す。`switch` では `never` を使った網羅チェックを入れる。
- IDは素の `string` ではなく、ブランド型（`CustomerId`、`StoreId` など）にする。

## 2. 状態とデータ

- `GameState` に、クラスのインスタンス、関数、`Map`、`Set`、`Date` を入れない。
- バランスに関わる数値（原価、価格、家賃、客の好み、成長の天井など）は、コードに直書きせず `packages/content` のデータに置く。
- ゲーム内に表示するテキストはコードに直書きせず、まとめて管理する。

## 3. お金と数値

- お金は**整数（円単位）**で持つ。小数で計算しない。
- 割合や倍率で計算したあとは、どこで丸めるかを決めて、共通の関数で丸める。

## 4. 乱数と時間

- 乱数は必ずシード付きのものを `ctx` 経由で使う。`Math.random()` は使用禁止。
- `Date.now()` などの実時間を扱ってよいのは `packages/app` だけ。`packages/domain`、`packages/application`、`packages/adapters` では使わない（`docs/architecture.md` 5.4）。

## 5. 純粋性

- `packages/domain` の関数は、引数の状態を直接書き換えない（新しい状態を返す）。
- `packages/domain` から、ネットワーク、ストレージ、DOMなどの外部に触れない。

## 6. 非同期

- `packages/app` で非同期処理を使うときは、Promiseを放置しない（`await` するか、エラー処理を付ける）。
- ESLint の `no-floating-promises` を有効にする。
- `packages/domain` には非同期処理を入れない。`packages/application` の `tick` と `advance` も同期処理にする（非同期はポートを使う処理だけ：`docs/architecture.md` 5.2）。

## 7. テスト

- 各systemに単体テストを書く。「この状態・この入力なら、この結果」の形にする。
- シード固定の通しテストを置く（例: シード42でゲーム内30週回したときの売上・評判・在庫のスナップショット）。
- 長期間のシミュレーションを高速で回して、「すぐ倒産しないか」「儲かりすぎないか」を確認するバランステストを用意する。

## 8. 変更の進め方

- 1つのブランチ・1つのPRは、1つのissueに対応させる。変更は小さく保つ。
- PRには、何を・なぜ変えたか、関連するissue番号、テスト結果を書く。
- 担当外のフォルダは触らない。触る必要があるときは、理由をPRに書く。
- 型チェック、lint、境界チェック、テストがすべて通ってからPRを出す。

## 9. 書き方

- 名前は英語、コメントとドキュメントは日本語。
- 1つの関数・1つのファイルは小さく保つ。
- コメントには「何をしているか」より「なぜそうしているか」を書く。
